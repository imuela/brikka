# BRIKA — AI SPECIFICATION V1

## Arquitectura

Domain/Application → AI Gateway → Provider.

## Objetivos

Desacoplar el dominio de proveedores de IA y controlar seguridad y costes.

## Casos de uso

Posibles funciones V1:
- extracción de datos documentales;
- resumen;
- asistencia al broker;
- detección de documentación;
- generación asistida de comunicaciones.

Cada caso de uso deberá aprobarse funcionalmente antes de implementarse.

## Seguridad

La IA sólo recibirá datos autorizados.

No se enviará información de un tenant a otro.

## Trazabilidad

Registrar:
- empresa;
- usuario;
- operación;
- proveedor;
- modelo;
- operación IA;
- tokens;
- coste estimado;
- timestamp.

## Principios

IA como asistencia, no como autoridad final en decisiones hipotecarias.

## Proveedores V1 (Sprint 33/34)

Dos abstracciones de proveedor distintas, cada una con su propio motivo (ver `12_DECISION_LOG.md`
D10-2/D10-3 y la adenda Sprint 34):

- **`AiProvider`** (Java, síncrono): `summarize`/`explain`/`draftMessage`. Solo `NoOpAiProvider`
  implementado — ningún proveedor externo aprobado para estos 3 casos de uso.
- **Extracción documental** (`DocumentExtraction`, vía `AiTaskDispatcher` → `ai-worker`,
  asíncrono): el Worker Python selecciona su propio proveedor mediante la variable de entorno
  `AI_PROVIDER` (leída solo por el proceso Python, nunca por Spring Boot):
  - `AI_PROVIDER=anthropic` (o sin definir, con `ANTHROPIC_API_KEY` presente — comportamiento
    Sprint 33 preservado sin cambios): llamada real a la API de Mensajes de Anthropic. Soporta
    PDF/imagen/texto/HTML. Requiere `ANTHROPIC_API_KEY` (de pago, externo).
  - `AI_PROVIDER=ollama`: llamada real a un servidor Ollama local. Gratuito, sin API key, sin
    coste por llamada. Solo texto/HTML (`text/plain`, `text/html`) — sin modelo de visión por
    defecto (ver limitación abajo).
  - `AI_PROVIDER=none` o sin ninguna de las anteriores: comportamiento honesto `NoOpAiProvider`
    de siempre — ningún proveedor configurado, `NO_PROVIDER`.

### IA local con Ollama (Sprint 34)

**Requisitos:** macOS/Linux/Windows con Ollama instalado (~200MB) + ~1.3GB de disco para el
modelo por defecto + RAM suficiente para inferencia en CPU (modelo de 1B parámetros: cómodo en
cualquier portátil de desarrollo moderno).

**Instalación:**
```bash
brew install ollama          # macOS; ver ollama.com/download para otros sistemas
ollama serve                 # levanta el servidor local en :11434 (o como servicio de brew)
ollama pull llama3.2:1b      # descarga el modelo por defecto (~1.3GB, una sola vez)
```

**Configurar Brikka para usarlo** (`.env`, nunca commitear valores reales de proveedores de pago,
pero Ollama no tiene secretos que proteger):
```
AI_WORKER_TRANSPORT=http
AI_PROVIDER=ollama
# OLLAMA_BASE_URL=http://localhost:11434   (por defecto, normalmente no hace falta cambiarlo)
# OLLAMA_MODEL=llama3.2:1b                 (por defecto)
```

**Cambiar de proveedor:** cambiar `AI_PROVIDER` a `anthropic` (y definir `ANTHROPIC_API_KEY`) o a
`none`/vacío para desactivar la IA documental por completo — sin tocar código.

**Limitación documentada (D34-AI-1):** Ollama aquí es deliberadamente solo texto. Ningún modelo
Ollama con capacidad de visión viene instalado por defecto (los modelos multimodales ocupan
varios GB, explícitamente descartado por el propio encargo del sprint — "no instalar un modelo
enorme"). Analizar un PDF o una imagen con `AI_PROVIDER=ollama` devuelve un resultado
`FAILED` honesto ("Unsupported document type for this AI provider") en vez de inventar una
extracción — no un error genérico ni un 500. Para PDF/imagen, usar `AI_PROVIDER=anthropic`.

**Comportamiento sin Ollama corriendo o con un modelo inexistente:** ambos casos se reportan como
`FAILED` con un mensaje de advertencia explicativo (conexión rechazada / HTTP 404 del modelo) —
nunca un crash del Worker, nunca un resultado inventado. Cubierto por
`ai-worker/tests/test_main.py::OllamaProviderExtractionTests` contra un servidor Ollama falso (no
depende de tener Ollama instalado para pasar en CI).
